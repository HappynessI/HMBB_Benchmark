# 本次改动

## 1. 独立制定 Rubric 2.0

直接触发这次调整的是一次试跑：客户回复内容冗余、一次给出多个排查方案，不符合对接方文档的沟通要求，却拿到了高分。为避免“知识点齐全”掩盖实际使用问题，新增本轮决策、客户信息负担、自然表达等维度，评价当前节点应发送的下一条回复。规则与评分器仍需共同校准。

| 维度 | 分值 | 业务含义 |
|---|---:|---|
| 业务要点 | 30 | 事实、条件和必要风险是否正确 |
| 本轮决策 | 20 | 此时应该直接回答、追问还是排查 |
| 客户信息负担 | 20 | 客户是否清楚现在只需回答或做什么 |
| 自然表达 | 15 | 是否自然具体，避免套话与内部术语 |
| 事实依据 | 10 | 内容是否有现行来源支持 |
| 内部支持 | 5 | 客服是否知道后续触发条件与动作 |

每项为 excellent / adequate / poor，对应 1 / 0.5 / 0。业务要点按原相对权重归一到 30 分。严重错误按规则封顶；资料冲突或无法判断时标记待复核，不强行给分。

权重与封顶值是本次设计选择，尚非业务验收标准。原 rubric、Skill、题目和知识库保持原样。完整规则见 [rubric.yaml](../rubric/rubric.yaml)，执行要求见 [评分说明](../rubric/评分说明.md)。

## 2. 增加客户沟通 prompt

独立增加 [customer_style_v1.txt](../prompts/customer_style_v1.txt)，不覆盖原 Skill：

- 一轮聚焦一个关键追问或一个排查阶段，等待反馈。
- 型号、灯态、场景允许分轮确认，但必须在依赖这些信息的操作之前确认。
- 以 2–4 个自然短句为目标，不设机械字数上限，不牺牲必要风险提醒。
- 后续分支放在内部“下一步”，不一次全部发送给客户。

组合方式：实验基础指令＋风格补充指令＋原 Skill＋后端接入说明；题目会话与检索证据随后提供。风格补充约束表达方式，业务事实仍以现行知识为准。

## 3. 保留首次结果与复核记录

同一道新题分别测试 LLM-Wiki 和 Utopia，每组只生成一次。后续评分只读取保存的答案，没有为了评分重新作答，也没有挑最高分。结果见 [单题结果](../results/单题结果.md)。

仍需解决：未经确认就下结论、分轮追问的扣分边界、自然度评价偏宽，以及工具调用标记泄漏。短了不等于答对了，单题高分不等于后端整体更好。
