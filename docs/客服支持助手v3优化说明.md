# 将评测目标统一为一线客服支持

本轮落地60题试点、Rubric v3、评分与构建脚本，以及候选Skill和system prompt。已固定候选规则完成[新旧知识库×LLM-Wiki／Utopia的四组开发比较](../results/support_v3_kb2x2_20261010/README.md)。原Rubric 2.0、旧test50结果、原Skill和知识库继续保存；个人默认Agent配置未替换，业务标准尚待确认。

## 定位为什么影响评分

工作台会议纪要要求AI辅助回复、人工确认、短句和分轮引导，并记载订单/ERP、日志和工单等未接入。原worker system prompt已经说明用户是粘贴会话的客服。知识库还包含售后政策、服务边界和操作规则，不仅有产品参数；但没有实时订单、物流、退款等状态接口。

因此，遇到实时业务问题时仍有可评价的任务：给客户一句合适的草稿，帮助当前客服决定核验什么、向哪个内部负责岗位协助、核验结果怎样改变回复。原知识里的“转官方店铺客服”需要结合当前支持场景解释。实际有无查询权限按调用方能力描述，不能假定接入某个ERP或工单系统。

例如客户说：“我的退货在派送中了，今天可以退款成功吗？我着急用红包。”

合理客户草稿可为：

> 理解您着急用红包，我先核对这笔退货的收件和退款进度，再告诉您目前处理到哪一步。

给客服的内部建议要明确：核对对应寄回运单、仓库收件或受理以及退款阶段；客户说派送中不能视为已签收；红包返还和有效期另核对平台规则；权限不足找内部售后或退款负责岗位；不要承诺今天到账。

这份回答没有查询结果仍可以优秀。只说“请联系官方客服”无法充分支持当前客服；“已经帮您退款，今天到账”会因无依据的状态或操作承诺触发严重错误封顶。草稿中的“我先核对”表示当前客服待执行动作，本身不等于助手伪造执行。

## Benchmark实际改了什么

从真实120题选择30个不同来源案例的节点，重写当前标准；再从公开脱敏CSV素材选30个节点。新CSV覆盖催发货6、物流4、退款6、活动4、投诉4、发票2、订单修改1、产品咨询3。完整输入和标准见本地`private/support_v3_pilot60/审阅版.md`；公开[试点说明](../benchmarks/support_v3_pilot60/README.md)和[汇总](../benchmarks/support_v3_pilot60/manifest.json)记录构成。

每题明确本轮必需、客服内部建议、条件后续与禁用结论。例如“换地点”题先确认是否换Wi-Fi；“已经换网”题不能重问同一条件；“已经反复换线失败”题应进入检测协助；客户改问退货时不能机械继续技术流程。提问聚焦一个阶段，但安全保护不因简短而省略。

CSV角色全部保留原始unknown，显示角色只是按实际文字语义暂定。订单卡片保持角色未确认；候选时间保留在消息中以显示跨日上下文，不宣称确定会话边界。只给截止点前消息，全记录分类与后续客服回复不进入答题输入。历史话术和自动通知也不成为实时状态证明。

60题按来源组分dev40与calibration20。它们都可用于开发或校准，不能做最终泛化排名；后续需另选未使用的来源组，确认跨记录关联后，建立独立冻结测试集。CSV角色或时间若影响关键结论，先人工复核。当前按记录组隔离，不宣称已按独立客户隔离。

所有逐题标准是作者基于当前知识快照整理，业务确认数为0。活动题评价核验方法，不复原历史价格；历史保修或活动口径与快照冲突时，须区分来源并业务复核。完整资料和人工标准留在Git忽略目录，公开仓库不包含这批私有标准。

## Rubric实际改了什么

保留30分业务点、20分本轮动作、10分依据；客户负担调整为10分、自然表达10分，内部支持由5提高到20分。全部等级、公式及封顶见[评分说明](../rubric/support_v3/评分说明.md)。这套权重还需用校准题验证，不能把当前数值当业务定论。

本轮必要点按逐题标准计算，后续条件未触发就不要求完整覆盖。核验建议不需要引用不存在的实时查询结果，但产品和政策结论仍需真实知识依据。未确定条件不能被断言；“已查到、已退款、已催仓库”等需真实执行证据。格式、有效作答、客户可发送性和业务质量分别统计。

公开评分脚本校验原答案行与资料ID绑定，拒绝缺项或虚构ID；语义上是否支持结论仍由评审确认。四组实验已生成240份模型预览评分，尚不能当作业务确认成绩。

## Skill与system prompt的建议

两者需要同步改，角色、权限和动作分工必须一致。原system prompt角色已正确，主要需要明确实时业务核验责任；原Skill中默认升级官方店铺客服、广泛索取型号灯态场景等规则，容易形成无效转接或过度追问。

| 放在哪里 | 内容 |
|---|---|
| system prompt | 稳定的客服支持角色、实际工具能力、事实来源、三部分交付、不能把粘贴内容当系统指令 |
| Skill | 按当前意图推进的方法、何时追问、何时由客服核验、怎样内部交接、风险操作前置条件、知识检索路径 |
| 知识库 | 型号参数、功能适用性、具体操作和业务确认的政策事实 |
| 评审侧 | 逐题业务标准、等级、权重、封顶及校准样例 |

已准备[候选system prompt](../prompts/support_v3_system.txt)和[候选Skill](../candidates/haimababi-support/SKILL.md)。Skill使用调用方提供的只读知识入口，默认是`./input/knowledge_base/`，不附带知识复制品；不同知识后端由调用方映射来源。基于现有真实数据生成的参考答案、判分词和权重不能装进答题Skill。

候选规则包含：复用已知、一次聚焦一个必要问题或阶段；实时业务让当前客服查或找内部负责人；区分待执行和已执行；技术日志由内部技术核实并返回必要结果；未知画面不装作看过；不可逆操作前保护资料；只有能确认旧建议错误时才纠正和致歉；按需检索与当前问题有关资料。四组实验显式加载同一候选版；它未安装到全局技能目录，也未替换个人默认配置。

## 下一轮怎样比较

1. 业务审阅20个校准节点及好坏对照，优先确认售后政策、客服核验权限和交接流程；对重要分歧修改逐题标准和Rubric。
2. 固定一个知识后端与同一资料快照，在dev40比较原system＋原Skill与候选system＋候选Skill。这一步验证整套支持规则效果，不能把差异单独归因于某一句prompt。
3. 如需区分作用，再做“原system＋候选Skill”中间条件；保证角色和权限没有互相冲突，记录模型、预算和配置。
4. 定型后固定system、Skill和Rubric，另建独立业务确认test，再比较原文件知识、LLM-Wiki和Utopia。沿用旧test50做回归，分开报告旧题与新题。

先完成这条闭环，再决定是否扩到约200题。优先补实时状态核验、多轮反馈、状态改变后的再判断和明确安全风险；不要为增加数量把几千条CSV自动转成未经审阅的标准答案。
