# 退货与退款

## 1. 适用范围

想退货、套餐拆退、退货期限、寄回后的退款进度、未发取消退款及退款到账。退款申请、仓库收件、审核、退款执行和资金到账必须分开。

## 2. 用户常见说法

能退吗、只退提醒器行不行、回去后发现不合意、派送中今天能退款吗、已经申请怕超期、信号不好想直接退。

## 3. 必查知识

本流程负责实时适用资格与阶段；一般政策资料在[售后安全](05_service_safety.md)，寄回轨迹在[订单物流](06_order_logistics.md)，红包与活动权益在[08](08_promotions_price_protection.md)。不把历史客服一段话当正式退款政策。

## 4. 处理流程

### 核验主链

1. **适用场景**：当前诉求是退货、退款或进度。先听当前目标，不能强制回到技术排查。
2. **已知与关键未知**：复用订单、签收、申请、物品状态、寄回线索和顾虑；适用规则、资格及当前阶段待核验。出差或长时间等待不能直接证明已过期。
3. **本轮动作**：回应客户想退/等待/担心期限，先由当前客服核验关键资格或阶段；信息不足只补必要定位。
4. **客户草稿示例**：“理解您担心处理时间，我先核对这笔退货的收件和退款进度，再告诉您目前到哪一步。”
5. **客服内部核验**：现阶段诉求→订单适用规则/资格→申请及寄回→实际收件/验收→审核/退款执行→到账；只检查当前适用分支，权限不足找售后或退款负责岗位。
6. **反馈后的分支**：资格确定给真实选项；阶段明确给下一实际动作。缺资料先补，已执行退款仍要区别平台/支付到账状态。
7. **停止排查或交接条件**：例外通融、套餐拆退、规则冲突、阶段停滞或权限不足时内部协调；不让等待技术排查消耗退货期限。
8. **风险与依据**：不承诺可退、全额、免费、今天到账；不让客户先撤申请或认为补发自动延长期限。涉及寄回设备/卡先按数据保护规则处理。

### 各场景的核验分支

| 当前诉求 | 必要核验 | 核实后的处理 |
|---|---|---|
| 因不合意或故障想退 | 渠道和订单规则、签收、商品状态、申请情况 | 符合规则给真实流程；不明或需例外找售后，不以出差叙述直接拒绝 |
| 排查中改为退货 | 当前客户目标与资格 | 先处理退货资格；客户愿意继续排查才走技术分支，已尝试记录用于交接 |
| 套餐配件单独退 | SKU组成、拆退权限、退款金额和赠品/优惠影响 | 资格确认才给拆退方案，不保证单配件全退，也不强制先退整机 |
| 未发货取消或已发拦截 | 当前订单/承运状态、取消或拦截权限 | 取消、拦截、退款不是同一执行结果；拦截申请详见09，不保证成功自动到账 |
| 寄回中问退款 | 寄回轨迹、实际收件/验收、申请和审核阶段 | 派送中不当已收；物流妥投不自动等于已审核；确认当前节点再说明下一动作 |
| 已退款但未到账 | 实际退款凭据、支付/平台状态与适用时效 | 核对到账渠道和阻塞，不把“已申请”当“已退款”，不编造银行时限 |
| 怕期限与补发冲突 | 适用截止、已有申请是否有效、补发真实安排 | 保留申请状态，核实可选方案，不劝先撤单，不承诺自动延期 |

## 5. 标准回答规则

资格要有适用规则与实际订单依据，重要冲突标待业务确认。红包、返券、运费险等有独立规则，不能从客户着急或旧话术推出一定恢复/赔付。客户“派送中”是陈述，当前客服核实仓库阶段。

## 6. 常见问答

### 今天能退款成功吗？

助手无法知道实时状态。给当前客服具体收件、审核、执行或到账核验项；查到适用规则和实际阶段后再答，不用“我帮您申请了”掩盖未知。

### 客户已经申请退货，还要先取消等补发吗？

不要默认如此建议。核实截止、申请状态和补发选择，避免让客户丧失已有处理机会；具体可行性由业务负责岗位确认。

## 7. 复杂场景处理

支架危险加退货期限，先03保护，再并行核验期限与补发。重要录像设备寄回时先确认资料保护与隐私安排，不能先格式化再讨论。技术故障不自动赋予或取消退货资格。

## 8. 需要追问的情况

只补当前定位/资格/阶段必需信息，已有订单卡或申请不重索；权限可内部核验的信息优先内部查，减少客户负担。

## 9. 需要转人工的情况

售后资格、例外、拆退、期限或退款阶段需要内部售后/退款/履约协助时，交接现有记录和具体问题，请对方返回实际状态或明确可行方案。助手不代办、不假定工单系统存在。

## 10. 来源索引

旧服务边界与政策快照、MVP和开发诉求。流程是核验设计；退货时限、到账时间、运费、赠品金额与红包权益全部以可靠资料或实际业务确认为准。
