# 检索与冲突处理规则

## 产品识别

先判断当前诉求是否依赖型号。活动、订单和发票问题直接走对应意图，不要求先遍历全部产品。产品有歧义时查看`aliases.yaml`的`ambiguous_aliases`，候选范围不是确定型号；“二代”“黄色款”“4K款”不能强行归一。

已知具体型号读对应产品；只有不同型号会改变答案或操作时才向客户问一个必要条件。口语“换新”可能指焕新版，也可能指售后更换，结合语境判断，不能一律当SKU。

## 文档优先级

1. 按当前问题查必要意图分支和相关产品。参数用专属文档，对比用规格/功能矩阵，适配用兼容矩阵；只读取足以支持当前阶段的内容。
2. 操作必须有型号、版本、状态与场景适用依据；旧通用教程缺适用范围时不能强套。逐步补必要信息，而非一次收全。
3. 全局能力和边界优先约束具体教程；立即风险先保护，数据操作先保护资料，交易状态由当前客服核验。
4. 政策、安全入口见`20_intents/05_service_safety.md`；交易详细流程见06—09文档。保修与退款规则不能由历史营销推导。
5. `_archive/`不进入默认检索和客户依据；只供人工追溯旧来源，不覆盖候选流程。

## 来源与归因

| 来源 | 可用来做什么 | 不能直接推出什么 |
|---|---|---|
| 当前可见客户陈述 | 表示客户报告的现象、诉求、尝试及时间 | 已确诊原因、仓库收件、实际到账 |
| 产品知识与矩阵 | 对应快照的参数、功能和适配，保留条件 | 当前活动、未收录菜单、医疗有效性 |
| 历史客服/自动通知 | 沟通与承诺线索，供当前客服复核 | 已实际执行、当前物流、正式政策 |
| 订单卡片/截图文字 | 辅助定位订单或页面，注明来源及时间 | 实时状态、卡片发送者身份或未附画面 |
| 当前人工核验结果 | 在对应对象和时间范围内回复实际进展 | 未核验的其他订单、后续结果保证 |

“依据”写知识路径与章节、会话来源和关键未知。核验建议是处理方法，不需要捏造实时查询资料。页面显示和快照价格仅历史事实；客户问现在多少钱，必须核对当前条款，不能只换成非承诺措辞。

## 冲突处理

资料的真实发布方、日期、型号和适用条件优先核实；不能因为文档名字有“官方”就视为已验证。产品参数参考原优先级：明确官方说明书/官网 > 商品页 > 客服问答 > 评论；同源冲突仍保留。

既有三代分辨率`2880 x 1620`与尺寸`137 x 88 x 108 mm`继续作为所提供快照记录，不新增推导。型号专用文档与矩阵冲突时标待核验；配件只支持明确变体，不跨型号外推。

7日、12个月、365天营销、免费换新或维修口径有范围差异时，不合并成统一承诺；交售后或规则负责岗位核实。原料不足可推进最小核验动作，但不能伪造确定政策。

## 安全与医疗边界

沿用[客服回答边界](00_global/customer_service_boundaries.md)：辅助看护、不保证100%、宝宝异常先人工查看，严重或持续异常及时就医。客户只问功能不编造健康状况。小夜灯与音频的必要提醒写在相关使用节点。

## 找不到依据

1. 区分“缺产品/操作资料”和“缺实时状态”。前者请内部产品或技术岗位确认适用能力/入口；后者请当前客服查对应订单或申请，权限不足找内部负责岗位。
2. 内部说明具体缺什么、查什么和核实后改变哪个处理分支，不只说“转人工/以页面为准”。客户草稿用自然话表达核对意图，无需说“知识库没有”。
3. 有可见信息先复用；缺定位或型号时只补最少信息。截图未附或OCR未接入时不装作看过，必要时用文字确认或建议人工查看。
4. 未核验前不发确诊、结果和时限；已失败、资料不足或有风险时停止无依据试错，整理必要交接。

## 开发来源与评测隔离

流程设计只使用MVP要求、原知识快照和已标识的开发会话前缀发现诉求。评测题、逐题标准、权重、评分锚点与未来测试来源不进入知识。会话中的长话术不直接变成政策或操作依据。来源组索引留在知识目录外的维护报告，作答只读manifest列出的active_documents。
